CLAUDE CODE MASTER BUILD PROMPT

Project: Qattice Cryptographic Research Lab (QCRL)

Version 0.1 — Mathematical Discovery and Cryptographic Primitive Research Sandbox

You are acting as a senior Rust systems engineer, computational mathematician, post-quantum cryptography researcher, and security-focused software architect.

Your assignment is to design, implement, test, and document a complete standalone research environment called Qattice Cryptographic Research Lab (QCRL).

This is a serious experimental mathematics and cryptographic research program, not a production cryptography library.

1. Mission

Build a modular, reproducible research sandbox capable of:

1. Investigating mathematical structures relevant to cryptography.
2. Designing and testing original mathematical algorithms.
3. Experimenting with lattice-based and hash-based constructions.
4. Exploring post-quantum zero-knowledge proof optimization.
5. Researching compact representations of cryptographic relations.
6. Simulating attacks against experimental primitives.
7. Comparing experimental constructions against established baselines.
8. Recording mathematical discoveries, conjectures, failures, and reproducible results.
9. Supporting future research into entirely new cryptographic primitives.

The laboratory must support both the integration of existing mathematical techniques and the exploration of original constructions.

Primary research philosophy: Mathematical discovery first, rigorous validation second, cryptographic application only after substantial evidence.

Do not claim that a mathematical construction is secure merely because tests pass.

2. Development Environment

Target hardware:

- Windows laptop
- Ubuntu under WSL2
- VS Code with WSL integration
- 16 GB RAM
- NVIDIA GTX 1660 Ti
- Rust stable toolchain
- Python 3 virtual environment

Requirements:

- CPU-first execution.

- No paid APIs or cloud services required.
- Respect memory and CPU limits.
- Never require administrator/root privileges during ordinary execution.
- Store the repository within the Linux filesystem, not "/mnt/c".
- Provide documented setup and launch commands.

The project must be completely independent of the existing QCB Chain and Chain Forge repositories.

No access to production wallets, validator keys, mainnet credentials, or live blockchain nodes.

4. Mathematical Engine

Implement a Rust mathematical experimentation library supporting:

- Modular integer arithmetic.
- Modular inverses where they exist.
- Polynomial addition and multiplication.
- Polynomial reduction modulo specified relations.
- Vector and matrix arithmetic.
- Basic finite-field operations.
- Small-dimensional lattice examples.
- Norm calculations.
- Reproducible random instance generation.

Use established Rust libraries where appropriate.

Prefer correctness, readable implementations, and explicit error handling over premature optimization.

Use property-based testing to verify mathematical identities.

Use Python and SymPy as an independent mathematical reference for selected tests.

5. Lattice Research Engine

Create a research module for studying mathematical structures related to lattice cryptography.

Initial experiments:

- Polynomial rings used in lattice constructions.
- Modular arithmetic under varying parameters.
- Small-dimensional lattice problems.
- Matrix transformations.
- Representation size.
- Computational complexity.
- Parameter sensitivity.

Provide toy examples illustrating concepts associated with LWE, Module-LWE, and Module-SIS.

These are educational and experimental implementations only.

Do not claim equivalence to standardized ML-DSA security.

Use publicly documented ML-DSA specifications as reference material, without modifying or replacing its production cryptographic implementation.

6. Experimental Primitive Laboratory

Create a modular interface for registering experimental mathematical and cryptographic constructions.

Each candidate must have:

- Unique identifier.
- Version.
- Mathematical definition.
- Intended purpose.
- Input and output specifications.
- Parameter set.
- Explicit assumptions.
- Claimed security goals, clearly marked as hypotheses.
- Known weaknesses.
- Benchmark results.
- Reproducible test vectors.
- Development status.

Support research categories including:

- Hash function candidates.
- Commitment constructions.
- Signature-related mathematics.
- Zero-knowledge proof components.
- Credential presentation components.
- Proof compression methods.

Do not attempt to implement every category immediately.

Implement one minimal, working example first.

Experimental primitives must never be exposed as production-safe cryptographic APIs.

7. Mathematical Discovery Engine

Create "qcrl-discovery" as a framework for automated mathematical experimentation.

It must support:

1. Defining a mathematical hypothesis.
2. Selecting a finite parameter search space.
3. Generating candidate mathematical transformations.
4. Checking candidate properties.
5. Searching for counterexamples.
6. Recording successful and failed experiments.
7. Reproducing results using deterministic seeds.
8. Comparing candidate performance.
9. Exporting results as JSON and CSV.

The initial discovery algorithm should investigate polynomial transformations over finite rings.

For example:

Can a transformation preserve a specified algebraic relation while reducing its representation cost or computational complexity?

Implement a bounded search that generates small candidate transformations, tests the required identities, and records counterexamples.

Use exhaustive checking when the search space is small enough.

Clearly distinguish:

- Verified finite-domain properties.
- Empirical observations.
- Unproven conjectures.
- Formally proven statements.

A candidate passing tests must never automatically be labeled a mathematical discovery or secure cryptographic primitive.

8. Cryptographic Attack Simulator

Build a testing module that attempts to identify weaknesses in experimental constructions.

Initial capabilities:

- Hash collision searches for deliberately small toy domains.
- Avalanche-effect measurement.
- Output distribution analysis.
- Determinism and reproducibility checks.
- Boundary-condition testing.
- Malformed-input testing.
- Small-parameter exhaustive attacks.
- Property-based counterexample generation.

Later research extensions may include:

- Forgery experiments.
- Algebraic distinguishers.
- Information leakage analysis.
- Side-channel evaluation.
- Protocol-level unlinkability testing.

Clearly explain that statistical testing alone does not establish cryptographic security.

All attack experiments must operate on local research implementations and generated test data.

9. Proof Compression Research

Build a dedicated experimental framework to investigate representation efficiency.

Measure:

- Original representation size.
- Encoded representation size.
- Compression ratio.
- Encoding time.
- Decoding time.
- Memory consumption.
- Whether the original mathematical relation remains valid after decoding.

Start with lossless encodings of toy polynomial and lattice objects.

Compare against straightforward canonical serialization.

Do not confuse ordinary data compression with cryptographic proof compression.

A future cryptographic proof-compression candidate must preserve the relevant proof system's completeness, soundness, and zero-knowledge requirements.

10. Benchmarking and Experiment Reproducibility

Use Criterion.rs for Rust microbenchmarks.

Record:

- Experiment identifier.
- Source commit hash when available.
- Algorithm version.
- Parameter set.
- Random seed.
- CPU architecture.
- Available memory.
- Rust compiler version.
- Python version when applicable.
- Execution duration.
- Peak memory when measurable.
- Output size.
- Test result.
- Timestamp.

Export machine-readable reports.

Provide a comparison command for two experiment runs.

Do not invent benchmark measurements.

Do not compare optimized production cryptography against unoptimized toy implementations as though the results demonstrate superiority.

Every command must have meaningful help output and sensible defaults.

12. Research Integrity and Security Boundaries

Enforce these rules:

- Experimental constructions are not production cryptography.
- No production signing keys or credentials.
- No integration with live QCB consensus.
- No automated deployment of discovered algorithms.
- No unsupported claims of post-quantum security.
- No arbitrary execution of generated code without sandbox controls.
- Bound computation time, search space, and memory.
- Maintain reproducible experiments.
- Document failed hypotheses and discovered weaknesses.

Keep experimental mathematical algorithms isolated from trusted cryptographic dependencies.
